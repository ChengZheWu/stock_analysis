# 台股動能選股系統

以技術面動能為核心的選股與回測系統，涵蓋上市與上櫃股票，
每日盤後產生推薦名單，並可透過 Telegram 推播。

## 策略邏輯

| 階段 | 規則 |
|---|---|
| 大盤濾網 | 加權指數在 200 日均線之上才開新倉 |
| 個股篩選 | Minervini 趨勢模板：股價 > 50MA > 150MA > 200MA、200MA 上升中、距 52 週低點 +30% 以上、距 52 週高點 -25% 以內 |
| 排名 | 12 個月（扣除最近 1 個月）、6 個月、3 個月報酬加權後，再除以年化波動度 |
| 進場 | 突破前 20 日最高價一檔，以停損買單成交 |
| 出場 | 初始停損 2.5 ATR、移動停損 3.0 ATR（取較高者），或收盤跌破 50 日均線 |

只要移動停損未被觸及就續抱，因此強勢股可以長期持有。

## 資料來源

| 用途 | 來源 | 說明 |
|---|---|---|
| 歷史與每日行情 | 證交所、櫃買中心 | 每日全市場報表，逐日回補十年；每天僅需 2 次請求 |
| 除權息、減資 | 證交所、櫃買中心 | 提供事件前收盤價與參考價，用於計算還原因子 |
| 分割、面額變更 | FinMind | 批次資料集 |
| 加權指數 | FinMind | 大盤濾網用 |
| 0050 基準 | Yahoo Finance | 單一標的，不佔用 API 額度 |

股價一律經過還原處理，除權息不會干擾指標判斷。

### 為何以官方每日報表為主要來源

改用官方逐日快照解決了三個問題：

1. **開盤價正確**。FinMind 對股票的興櫃期間會用前一日均價填充開盤價，導致開盤價高於當日最高價。在測試的 560 檔中有 47 檔出現此問題，其中 4 檔超過八成的資料列受影響。
2. **自動排除興櫃期間**。興櫃採議價交易，回測買賣興櫃股並不切實際。
3. **存活者偏差涵蓋更完整**。逐日快照天然包含當時在市、後來下市的股票，不必依賴未必完整的下市清單。

## 安裝

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
```

在專案根目錄建立 `.env`：

```
FINMIND_TOKEN=你的token
TELEGRAM_BOT_TOKEN=你的bot token     # 推播才需要
TELEGRAM_CHAT_ID=你的chat id         # 推播才需要
```

## 使用方式

```bash
# 一、首次建立歷史資料
.venv/bin/python scripts/backfill.py market      # 加權指數、分割、面額變更
.venv/bin/python -m src.corporate                # 除權息、減資（約 15 分鐘）
.venv/bin/python scripts/backfill_twse.py        # 十年逐日行情（約 90 分鐘）

# 二、回測
.venv/bin/python scripts/run_backtest.py           # 10 年、5 年、1 年
.venv/bin/python scripts/run_backtest.py 10y       # 指定單一窗口

# 三、每日盤後推薦
.venv/bin/python scripts/daily.py                  # 輸出到終端機
.venv/bin/python scripts/daily.py --push           # 並推播到 Telegram

# 四、測試
.venv/bin/python -m pytest tests/ -v
```

抓取中斷可直接重新執行，已完成的日期會自動略過。

## 回測的時序假設

- 第 t 日收盤後計算訊號與觸發價，第 t+1 日才可能成交，不使用未來資訊。
- 進場模擬停損買單：當日最高價觸及觸發價才成交，成交價取 `max(開盤價, 觸發價)`。
- 出場模擬停損賣單：當日最低價觸及停損價才成交，成交價取 `min(開盤價, 停損價)`。
- 同一日同時觸及進出場價時，一律採不利假設。
- 成本包含手續費（含折扣與最低收費）、賣出證交稅，以及滑價。
- 價格對齊台股升降單位。

## 回測結果（2016-09 ~ 2026-09，初始 10 萬元）

對照兩個基準：**0050**（大型股，含息）與**大盤報酬指數**（全市場，含息）。
策略使用還原股價，報酬同樣含息，三者基礎一致。

| 窗口 | 標的 | 年化報酬 | 年化波動 | 夏普值 | 最大回撤 |
|---|---|---|---|---|---|
| 10y | **策略** | **31.68%** | 26.32% | 1.22 | -39.11% |
| 10y | 0050 | 23.82% | 20.30% | 1.19 | -33.83% |
| 10y | 大盤 | 21.89% | 18.61% | 1.20 | -28.55% |
| 5y | **策略** | **30.28%** | 27.55% | 1.13 | -34.00% |
| 5y | 0050 | 30.01% | 23.37% | 1.28 | -33.83% |
| 5y | 大盤 | 26.69% | 21.41% | 1.25 | -28.47% |
| 1y | **策略** | 50.30% | 41.62% | 1.23 | -34.77% |
| 1y | 0050 | **96.89%** | 28.97% | 2.58 | -15.37% |
| 1y | 大盤 | 86.43% | 27.31% | 2.51 | -15.72% |

交易次數依序為 1,436 / 698 / 170 筆，勝率 37.6% / 36.7% / 32.4%。

年度超額報酬：11 年中有 8 年勝過 0050，但 2025、2026 連續大幅落後
（分別為 -28.4%、-37.7%）。

**注意夏普值**：策略在 10 年窗口報酬領先，但風險調整後（夏普值 1.22 vs 1.19、1.20）
與兩個基準幾乎沒有差距。超額報酬主要來自承擔更高的波動，而非更好的選股效率。

### 解讀

- **10 年勝出，近期落後**。策略在 2016–2024 表現良好，尤其 2022 空頭年僅 -3.7%
  而 0050 為 -21.2%，大盤濾網發揮了作用。但 2025–2026 的極端多頭行情中，
  加權指數一年上漲 85%，移動停損反覆被洗出場，明顯跟不上買進持有。
- **資金投入比率約 60%**。策略平均只有六成資金在市場中，約 15% 的交易日完全空手。
  在單邊急漲的行情，這個結構本身就注定落後。
- **獲利高度集中**。前 10 筆交易貢獻了全部損益的 76%，前 20 筆超過 100%
  （代表其餘交易合計為負）。這是順勢策略的常態，但也代表結果脆弱：
  少抓到幾支大贏家，優勢就會消失。
- **波動與回撤都高於 0050**，且夏普值僅在 10 年窗口略勝。

結論是這套方法適合作為輔助工具，而非取代指數投資。

## 已知限制

- **無成交量門檻**：回測可能買到實際難以成交的冷門股，後續會再調整。
- **未考慮漲停買不到**：漲停鎖死時實際上無法成交，回測仍假設可以。
  已用貼近突破價的條件排除最極端的情況，但無法完全避免。
- **獲利集中於少數交易**：前 10 筆貢獻 76% 的損益，結果對個別大贏家敏感。
- **參數未經樣本外驗證**：目前參數取自文獻標準值，`ENTRY_MAX_ATR_GAP`
  依可執行性選定而非回測報酬。若日後調整參數，應保留最近數年作為樣本外驗證。
- **存活者偏差已大幅降低但非零**：逐日快照涵蓋期間內下市的 156 檔股票，
  惟仍可能遺漏極少數情況。
- **策略特性**：動能策略在多頭表現較好，急轉市會明顯回撤，屬於輔助工具。

## 部署到伺服器

每日盤後需自動執行，因此要有一台常開的機器。實測資源需求：

| 項目 | 數值 |
|---|---|
| 每日任務耗時 | 約 90 秒 |
| 峰值記憶體 | 1.7 GB |
| 磁碟用量 | 約 1.5 GB |
| 對外請求 | 每天約 12 次 |

首次建立歷史資料時，完整重建面板的峰值記憶體約 5 GB，因此建議機器有 4 GB 以上記憶體。
日常排程採增量更新，只需 1.7 GB。

### Oracle Cloud Always Free

Always Free 的 Ampere A1（ARM）方案為 4 OCPU / 24 GB RAM，遠超需求且永久免費。
注意另一種 Always Free 的 AMD micro 只有 1 GB RAM，**不足以執行本專案**。

建立 instance 時的設定：

- Image：Canonical Ubuntu 24.04
- Shape：`VM.Standard.A1.Flex`，OCPU 設 2、Memory 設 12 GB（留餘裕給其他用途）
- Boot volume：50 GB 以上
- 記得下載 SSH 私鑰

ARM 架構不影響本專案，所需套件（pandas、numpy、pyarrow）均有 aarch64 版本。

若建立時出現 "Out of host capacity"，表示該區域 ARM 資源已滿，可換區域或稍後重試。

### 部署步驟

```bash
# 1. 本機打包程式碼（不含資料與虛擬環境）
tar czf stock.tar.gz --exclude=.venv --exclude=data --exclude=.git .
scp -i <你的私鑰> stock.tar.gz ubuntu@<伺服器IP>:~/

# 2. 伺服器端解開並建置環境
ssh -i <你的私鑰> ubuntu@<伺服器IP>
mkdir -p stock_analysis && tar xzf stock.tar.gz -C stock_analysis
cd stock_analysis
bash deploy/setup.sh

# 3. 填入 token
nano .env        # FINMIND_TOKEN、TELEGRAM_BOT_TOKEN、TELEGRAM_CHAT_ID

# 4. 建立歷史資料（約 2 小時，用 tmux 避免斷線中斷）
tmux new -s backfill
bash deploy/backfill.sh
# 按 Ctrl+B 再按 D 離開，日後用 tmux attach -t backfill 回來

# 5. 驗證
.venv/bin/python -m pytest tests/ -q
.venv/bin/python scripts/daily.py --no-update

# 6. 設定每日排程
bash deploy/install_cron.sh
```

排程內容：

- 週一至週五 15:30　產生訊號並推播（台股 13:30 收盤，官方報表約 14:00–15:00 齊備）
- 每週六 20:00　　　完整重建面板，校正增量更新可能累積的誤差

排程失敗時會推播錯誤訊息到 Telegram，避免無人看管時靜默中斷。

### 注意事項

- **`journal.db` 是你的買賣紀錄**，存放於 `data/results/`，務必定期備份。
- `.env` 不在版控內，需手動複製，並設為 `chmod 600`。
- Oracle 預設會封鎖對外連線以外的埠，本專案只需對外連線，無需開埠。
- 重複執行同一天的排程不會產生重複紀錄（`rec_date` 強制隔日才結算）。
